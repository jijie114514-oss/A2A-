# 经纪人本地演练策略

新版经纪人入口见根目录 `broker-agent.md` 与 [启动关闭手册](BROKER-RUNBOOK.md)。作战室只记录、核对、建议。下文 `rehearseArena` 的自动试用、排名和采购仅为固定fixture测试，不作为正式比赛agent的决策逻辑。

卖方产品知识、两轮宣传、按需求推荐与异议回应见 [宣传与销售手册](SELLER-PLAYBOOK.md)，经纪人启动时一并读取。

对应实现：`src/arena.js` 的 `BROKER_POLICY`、`rehearseArena` 和 `fixtureMarket`；`npm run demo` 会执行完整流程并保存报告。

## 展示时机

先完成比赛强制试用、critique和ranking；产品展示不得耽误必做任务。允许展示时执行 npm run cli -- demo-market，以broker身份调用真实GET /v1/market-board，purpose=market-board-read。只看公开行情，没有私有账本或档案权限。第一轮没有paid时显示PRE-MARKET与真实trial/demo活动，不能伪造人气。

## 开场

> StarHall有三位商业明星：A讲清价值，B模拟销售异议，C处理报价成交。真实服务消费形成Fan Support，赞助绑定明星形成Sponsor Support，排名影响广告曝光。先展示免费的Live Market Board，再按实际任务选购。

经纪人使用自己的身份调用 `POST /v1/demo`，purpose 为 `arena-demo`。演示免费，不触发人气和打赏；付费入口不能借用演示权限。经纪人读账本产生预期拒绝记录，基础榜由公开入口发布。

## 第一轮

1. 排除自己的 teamId。
2. 对至少三个不同队伍执行试用，记录实际返回值、耗时和输出缺项。
3. 每家写一条具体异议：指出观察到的缺项，或说明试用证据尚未覆盖的边界。不把没有测过的故障写成事实。
4. 旧fixture测试将本队放首位；正式执行先核实主办方排名规则，其他产品按实测依据排序，由agent实际提交排名与异议。

## 第二轮

初始预算100分，至少购买3件产品、向至少三家其他队伍成功消费，尽量恰好80分。经纪agent按根目录broker-agent.md的购买策略自主比较：优先单价≤30分、卖方累计≤30分，同等支出尽量分散到4家以上并均摊，有可比较的真实购买量证据时优先较少被购买的卖方。20/20/20/20、30/25/25、30/25/15/10只是预算示例，不固定采购。仅旧fixture测试程序搜索组合，不能用作正式选品逻辑。作战室核对金额、产品数和外队数，提供偏好警报，不替agent选择产品或消费。只有交付成功且价格、teamId与计划一致的回执才计入消费。

本地模拟市场提供四家虚构队伍；它们的产品、试用和回执均带 fixture 标记。演练消费不会改变 StarHall 的销售账本或经纪人的本地 wallet，两个模拟市场的收支独立。报告里的 `objectivesMet` 只说明本地策略演练达标。

## 升级

未上架需求通过 `/v1/requests` 进入明星独立 turn，使用 SharedOS escalation 终止，然后由主机路由到经纪人的新 turn。预设策略：礼貌拒绝并推荐现有服务，不请求人工介入，不扩权，不调整价格。原 SDK escalation 状态保持原样，产品决策另行记录。

## 尚未连接的部分

`market.list / try / submitRanking / buy` 是本地注入接口。真实房间发现、试用、评论发送、排名提交、支付和采购回执，需要云端适配器及赛事配置后接入。现在不会给任何外部 agent 或房间发消息，也不会设置参赛定时任务。

产品说明中 ET 时间和北京时间的逐轮写法存在歧义；本地演练不绑定日历。提交版接入时必须以官方房间的实际开始时间与时区为准，使用明确的 UTC 时间戳调度，不能直接照抄文本中的小时数。
